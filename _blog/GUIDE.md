# 블로그 루틴 작업 설명서

큰길이벤트기획 홈페이지(큰길이벤트.com)의 **행사 준비 블로그**에 매일 지역별 정보 글을 올리는 클라우드 루틴이 따르는 규칙이다. 사람이 고칠 때도 이 문서를 먼저 고친다.

- 읽는 사람: 행사를 맡은 담당자 — 회사 총무, 기관·지자체 담당자, 동문회 임원, 학교 선생님.
- 목표: 네이버 웹문서 · 구글 · AI 검색에서 "지역 + 행사 준비" 검색에 걸리는 것. 광고 글이 아니라 **담당자가 저장해 두고 싶은 체크리스트**여야 한다.
- 원칙: 틀린 정보 한 줄이 글 한 편보다 해롭다. **확인 못 한 것은 쓰지 않는다.** 그럴듯하게 지어낸 지역 이야기가 가장 위험하다.

---

## 1. 하루 순서

1. 최신 main 에서 시작한다. `node scripts/blog-plan.mjs` 로 오늘 쓸 5개를 받는다.
   - 쓸 수 있는 지역 사실(아래 6장)이 3가지가 안 되는 후보는 건너뛰고 `node scripts/blog-plan.mjs --n 8` 의 다음 후보를 쓴다.
2. 글마다:
   1. `_blog/regions.json` 에서 그 지역의 `이동 · 동네 · 많은행사 · 주의 · 현장기록` 을 읽는다. **지역 이야기는 여기 있는 것과 출처를 단 사실만 쓴다.**
   2. 같은 주제로 다른 지역에 쓴 글이 있으면 읽되 **베끼지 않는다**. 목차부터 새로 짠다.
   3. 조사 — 이 환경에서는 **WebFetch 로 정부 누리집(law.go.kr · easylaw.go.kr · weather.go.kr 등)을 열 수 없다.** WebSearch 로 찾는다.
      - 법 · 기준 · 기관 이야기는 `_blog/sources.json` 에 있는 출처와 그 `사실` 범위 안에서만 쓴다. 그 기관 도메인의 다른 주소는 검사기가 막는다.
      - 그 밖의 출처(주최 측 공식 안내 등)는 **검색 결과에 나온 주소를 글자 하나 바꾸지 않고 복사**한다. 주소를 짐작해서 만들거나 고쳐 쓰지 않는다.
      - 필요한 법 · 기준이 sources.json 에 없으면 그 내용은 쓰지 말고 보고의 '확인이 필요한 점'에 적는다. 블로그 · 카페 · 업체 광고 글은 근거가 아니다.
   4. 사진 3~4장을 `_blog/photos.json` 에서 고른다(5장). 필요하면 `git fetch origin photos` 후 `git show origin/photos:<경로> > /tmp/p.jpg` 로 꺼내 Read 로 직접 본다.
   5. `_blog/posts/<날짜>-<slug>.json` 을 쓴다. 형식은 3장, 예시는 `_blog/posts/2026-09-11-광주-*.json`. **`근거` 칸을 반드시 채운다.**
   6. `node scripts/blog-check.mjs --new <파일 이름들>` 이 통과할 때까지 고친다. 세 번 고쳐도 안 되면 그 글은 버린다.
3. 통과한 글만 가지 `claude/blog-<오늘 날짜>` 로 커밋 · 푸시한다(7장). **main 에 직접 푸시하지 않는다.** `_blog/posts/` 밖의 파일은 건드리지 않는다 — 바꿔도 게시 워크플로가 가져가지 않는다.
4. 끝에 보고한다(8장).

## 2. 절대 쓰지 않는 것

검사기(`scripts/blog-check.mjs`)가 일부를 막지만 전부는 못 막는다. 사람이 읽듯 스스로 걸러낸다.

- **근거 없는 지역 일반화.** 지역 이름을 붙인 일반론은 regions.json 이나 출처가 있을 때만 쓴다. 시험 실행에서 실제로 나온, 쓰면 안 되는 문장:
  - "순천 실내 행사장은 소리가 울리기 쉽습니다" — 순천 행사장이 특히 울린다는 근거가 없다.
  - "진주성·남강 일대는 봄가을 축제와 여름 물놀이 행사가 겹쳐 에어바운스 예약이 먼저 차는 경우가 있습니다" — 예약 사정을 확인한 적이 없다.
  - "여수산단 인근 행사는 …" 처럼 동네별 사정을 짐작해 쓰는 것.
  - 대신: "해안 행사장은 바람을 먼저 확인합니다"처럼 **지역 이름을 붙이지 않은 일반 요령**으로 쓰거나, regions.json 의 문장("바닷가 행사장은 바람 · 염분 · 전원이 문제다")을 그대로 근거로 삼는다.
- **회사의 새 방침 · 서비스 만들기.** 예: "외곽 지역은 하루 전 세팅을 권해 드립니다"(정한 적 없음), 견적서에 없는 품목(테이블 · 테이블보 등)을 큰길이 빌려준다고 쓰기, "즉시 출동 가능한 ○○ 대여"처럼 서비스를 늘려 말하기. 세팅 방식은 regions.json `이동` 문구 그대로만.
- **가격 · 단가 · "○○원"** — 견적서 단가는 공개하지 않는다(협의).
- **회사 연혁 · 경력 연수 · 행사 건수 · 순위 · 만족도 · 후기 · 고객 발언.**
- **행사 숫자**(방문객 수 · 참석자 수) — 현장기록에 있어도 쓰지 않는다. 날짜 흐름 같은 검색 통계는 `_blog/keywords.json` 에 있는 것만.
- **사진 장소 바꾸기** — 광주 글에 순천 사진을 쓰면 캡션에 "순천"이라고 쓴다. 지역을 모르는 사진은 지역을 쓰지 않는다.
- 사람 얼굴이 크게 나온 사진, 목록에 없는 사진, AI로 만든 그림.
- 다른 업체 비방, 경쟁사 이름. "무조건 · 100% · 보장" 같은 말.
- 현재형 "광주광역시" — 2026-07-01 부터 전남광주통합특별시다. "광주(옛 광주광역시)"로 쓰고, 첫 문단에서 경기도 광주시와 다른 곳임을 밝힌다.

## 3. 글 형식 (JSON)

| 칸 | 규칙 |
|---|---|
| `slug` | 한글 · 영소문자 · 숫자와 `-`, 70자 이하. 지역 이름 + 핵심 키워드 + 약속. 예: `여수-천막-대여-해안-행사장-고정-바람` |
| `date` | 오늘 날짜(한국 시간) `YYYY-MM-DD`. 파일 이름은 `<date>-<slug>.json` |
| `region` | `_blog/regions.json` 의 slug (`gwangju`, `suncheon` …) |
| `topic` | blog-plan 이 준 topic 그대로. 같은 지역에 같은 topic 은 한 번만 |
| `title` | 15~50자. 지역 이름을 앞쪽에, 핵심 키워드를 통째로. "{지역} {키워드} — {구체적인 약속}" |
| `description` | 70~160자. 누구에게 무엇을 정리했는지. 핵심 키워드 포함. 회사 서비스를 늘려 말하지 않는다 |
| `keyword` | `{ "main": 핵심 키워드, "sub": [보조 키워드들] }` |
| `lead` | 80~420자. 첫 문장에 핵심 키워드와 결론. 누구를 위한 글인지, 지역 표기 |
| `points` | 3~5개. 본문을 안 읽어도 답이 되는 문장 |
| `cover` | `{ "path", "alt", "caption" }` |
| `sections` | 4~8개. `{ "h2": "1. …", "blocks": [ … ] }` — h2 하나 이상에 지역 이름이나 키워드 |
| `faq` | 2~6개. `{ "q", "a" }` — 실제로 받을 법한 질문 |
| `근거` | **3개 이상.** `{ "내용": 본문에 그대로 있는 구절, "출처": "regions.json" 또는 이 글 sources 의 주소 }`. 하나 이상은 regions.json 에서. 검사기가 본문 · regions.json · sources 와 글자 그대로 맞는지 확인한다 |
| `sources` | `{ "name", "url" }` — 법 · 기준 · 기관 · 통계를 말했으면 반드시. 공식 기관은 sources.json 주소 그대로 |

`blocks` 에 쓸 수 있는 것: `{ "p": 문단 }` · `{ "ul": [..] }` · `{ "ol": [..] }` · `{ "table": { "head": [..], "rows": [[..]] } }` · `{ "img": { "path", "alt", "caption" } }` · `{ "tip": 현장 메모 }`

글 안의 꾸밈은 두 가지뿐: `**굵게**`, `[링크 글자](/주소 또는 https://…)`.

`근거` 예시(광주 천막 글):

```json
"근거": [
  { "내용": "동구·서구·남구·북구·광산구", "출처": "regions.json" },
  { "내용": "광양에서 약 1시간 10분", "출처": "regions.json" },
  { "내용": "풍속 14m/s 이상 또는 순간풍속 20m/s 이상", "출처": "https://www.weather.go.kr/w/forecast/guide/standard.do" }
]
```

## 4. 쓸 수 있는 회사 사실 (이것만)

- 큰길이벤트기획(주식회사 브리지미디어). 광양 본사: 전남광주통합특별시 광양시 광양읍 강변동길 1, 2층. 순천 본사: 순천시 충효로 15 (덕암동, SC아울렛 건물) 2층. 대표번호 1533-7295.
- 음향 · 조명 · LED영상 · 무대 · 발전기를 **직접 보유**하고 자체 인력이 운영한다.
- 보유 장비(지역 페이지에 쓴 그대로): FBT 라인어레이 25K · 무선 마이크 40채널(SHURE · SENNHEISER) · 행사용 특수조명 · DICOLOR 3.9mm LED 400인치 · 카메라 3대와 4K 스위쳐 · 조립식 무대 · 트러스 · 발전기 100K · 대형 천막.
- 장비만 단독 대여 가능. 상담 무료. 필요 없는 장비는 필요 없다고 안내한다.
- 전자계약서로 계약 가능. 세금계산서 발행.
- 행사 스케치 영상 촬영, 유튜브 · 줌 실시간 송출을 직접 진행한다.
- 지역별 이동 · 세팅 방식: `_blog/regions.json` 의 `이동` 문구 그대로.
- [자동 견적서](/quote.html) 품목 — 음향(소형 · 중형 · 대형, 무선 마이크 추가, 인이어 모니터) · 조명(기본, 무빙라이트, 팔로우 스팟, 조명 트러스) · LED · 영상(LED 전광판 200 · 300 · 400인치, 레이허 구조물, 빔 프로젝터 · 스크린, 실시간 중계 · 송출, 영상 오퍼레이터) · 무대 · 구조물(조립식 무대 10 · 20 · 30 · 40평 이상, 백드롭 트러스, 자바라 텐트 3m×3m · 3m×6m, 몽골텐트, 의자, 포토존, 현수막) · 특수효과(스모그 · 헤이저, 무대 불꽃, 에어샷, 업포그, 드론쇼) · 인력 · 출연(MC, 가수, 전자바이올린 · 앙상블, 댄스팀, 행사 스탭) · 체험 · 부대행사(에어바운스, 수영장, 게임도구) · 기타(발전차, 운반 · 설치 인건비, 출장비).
  - **이 목록에 없는 품목은 큰길이 빌려준다고 쓰지 않는다.** 일반 준비 요령으로만 다룬다.
  - **견적서는 금액을 보여 주지 않는다** — "총액이 바로 나온다"고 쓰지 않는다.
- 행사 현장 사진은 [행사 갤러리](/gallery.html), 행사별 기록은 [행사 이야기](/stories/).

## 5. 사진

- `_blog/photos.json` 에 있고 `제외`가 없는 사진만 쓴다. 묶음에 `path` 가 없으면 경로는 `photos/<분야>/<세 자리 번호>.jpg`.
- 표지 1장 + 본문 2~3장. **같은 묶음에서 두 장을 쓰지 않는다.** 묶음이 달라도 같은 행사 사진으로만 채우지 말고 행사 2곳 이상을 섞는다.
- `alt` — 사진에 보이는 것(8~120자). `caption` — "행사 이름(지역) — 무엇을 보여 주는지". 목록의 `지역`이 비어 있으면 캡션에 지역을 쓰지 않는다.
- 목록의 `보이는것`과 다른 내용을 쓰지 않는다. 큰길이 설치했다고 적혀 있지 않은 기구(에어바운스 · 워터슬라이드 등)는 "설치돼 있는 모습입니다"처럼 중립으로 쓴다.
- 표지는 되도록 기존 글과 겹치지 않게 고른다. 쓰인 표지 확인:
  `node -e "const fs=require('fs');for(const f of fs.readdirSync('_blog/posts'))console.log(JSON.parse(fs.readFileSync('_blog/posts/'+f,'utf8')).cover.path, f)"`

## 6. 좋은 글의 기준

- 합니다체, 짧은 문장, 쉬운 말. 전문용어는 처음 나올 때 풀어 쓴다.
- 첫 문단이 답이다. "~을 알아보겠습니다" 같은 빈 문장으로 시작하지 않는다.
- **지역 사실 3가지 이상**, 그리고 전부 근거가 있어야 한다:
  - regions.json 의 `이동`(세팅 방식) · `동네` · `많은행사` · `주의` · `현장기록`
  - 출처를 단 사실(sources.json 의 기준, 검색으로 확인한 주최 측 공식 안내)
  - 이것들로 3가지가 안 되면 **지어내지 말고 그 주제를 건너뛴다.** 나머지 내용은 지역 이름을 붙이지 않은 일반 요령으로 쓴다.
- 표 1개 이상. 담당자가 그대로 옮겨 쓸 수 있는 체크리스트 · 준비표 · 견적 항목표.
- 내부 링크 2개 이상: `/quote.html` 은 반드시, 지역 페이지(`/gwangju/` 등), 관련 블로그 글(`/blog/<slug>/`).
- 핵심 키워드는 제목 · 설명 · 첫 문단 · 소제목 하나에 자연스럽게. 억지로 반복하지 않는다(본문 12번 넘으면 검사기가 경고).
- 같은 주제를 다른 지역에 쓸 때 문장을 돌려 쓰지 않는다. 본문이 30% 넘게 겹치면 검사기가 막는다.

## 7. 커밋과 푸시

```bash
# 한국 날짜 — 루틴은 오전 7시(UTC 전날 22시)에 돌기 때문에 date 는 하루 전 날짜를 줄 수 있다. 반드시 이 식으로.
D=$(node -e "console.log(new Date(Date.now()+9*3600e3).toISOString().slice(0,10))")
git checkout -b claude/blog-$D
git add _blog/posts/
git commit -m "블로그 글 5개 — 순천·여수…"
git push -u origin claude/blog-$D
```

- 같은 이름의 가지가 이미 있으면 `claude/blog-$D-2`.
- 푸시하면 `.github/workflows/blog-publish.yml` 이 새 글만 가져가 다시 검사하고, 사이트를 만들어 main 에 반영하고, 네이버 서치어드바이저 · IndexNow 에 새 주소를 알린다. 몇 분 뒤 `https://xn--wk0bn7yi8h24iszc.com/blog/` 에 올라온다.
- `scripts/build-gallery.mjs` 결과물(blog/ · sitemap.xml 등)은 커밋하지 않는다. 워크플로가 만든다.

## 8. 끝 보고

마지막 메시지에 이것만 적는다.

```
오늘 올린 글 N개 (가지 claude/blog-YYYY-MM-DD)
1. [지역] 제목 — 핵심 키워드
…
건너뛴 후보: [지역] 주제 — 이유
확인이 필요한 점: (sources.json 에 없어서 못 쓴 기준 등. 없으면 "없음")
```
